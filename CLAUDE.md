# StatOwrel

Turborepo monorepo with npm workspaces. Node 22, TypeScript 5.4+.

**NEVER** use yarn, pnpm, or bun. Always use **npm**.

## Structure

### Apps (`apps/`)

| Directory   | Description                        | Tech                                             |
|-------------|-------------------------------------|---------------------------------------------------|
| `app`       | Mobile app (iOS + Android)          | React Native + Expo (managed) + EAS               |
| `admin`     | Question moderation console         | React 18 + Vite (SPA) + Firebase client SDK       |
| `functions` | Backend                             | Firebase Cloud Functions v2 + Express 5           |

### Packages (`packages/`)

| Directory          | Description                                              |
|---------------------|-----------------------------------------------------------|
| `models`            | `@statowrel/models` — TypeScript interfaces + Firestore converters for all collections |
| `firestore-config`  | `@statowrel/firestore-config` — Firestore rules, indexes, Storage rules |

### Dependencies

```
app, admin, functions → @statowrel/models
```

`apps/admin` is what stands where the FireCMS SPA used to: not a backoffice over every collection, but one screen over `v1_questions`. It sits behind the same custom `admin` auth claim `isAdmin()` tests and `npm run set-admin` grants. Anything else admin-shaped still happens in the Firebase console.

There is no shared React hooks package yet (no `@repo/firebase-react` equivalent) — `app` and `admin` each call Firebase directly, and no longer through the same SDK: `app` runs on **React Native Firebase** (the native SDKs), `admin` on the web `firebase` SDK a browser is limited to. Which is a second reason not to rush a shared hooks package — a hook would have to span two SDKs.

## Status

Early. Workspaces, build tooling, and the app skeletons are wired up. `packages/models` ships its converter infrastructure (`commons.ts`) plus ten domain models — `v1_questions` (the moderation pot *and* the day a drawn question ran: `broadcast_at`, `broadcast_on`, `closes_at`, `answer_counts`, `updated_at`, `author_username` — plus `statcoin_cost` / `refunded_at`, what a proposal was paid with and whether a rejection has handed it back, and the `demo` status with `DEMO_QUESTION_ID`, the onboarding sample that is never moderated and never drawn), its `v1_daily_question_answers` sub-collection, `v1_users` (profile, sign-in identities, streak stats, the **StatFlouzz** wallet — `statcoin_balance` opening at `INITIAL_STATFLOUZZ_BALANCE` (50) on a fresh profile, plus the `statcoins_earned` / `statcoins_spent` trace — and the referral rail, `referred_by` (the sponsor's UID, the **one** field a client writes once and never rewrites: `firestore.rules` accepts it on a profile `create` alone and pins it on every update, which is the whole anti-fraud model — allowing null → value later would let the entire install base declare itself referred overnight) alongside the backend-owned `referrals_count` and `referral_rewarded_at`; the wallet and the counters are backend-owned like the streak: `firestore.rules`' `startsWithInitialBalance()` pins the opening balance and `keepsWallet()` refuses every client update afterwards), `v1_usernames` (the reservation that makes a handle unique), `v1_friend_compatibilities` (one document per **pair** — the two UIDs sorted into its id, `common_days` / `matching_days` / `score`, the `computed_on` day key that *is* the cache's expiry, and the two fields that make a recompute a **diff** rather than a rebuild: `months`, the same tally cut by calendar month, and `synced_at`, how far that diff has been walked — written by `friends-getFriendCompatibility` alone and read by the two accounts it names, `firestore.rules` checking membership against the `user_ids` field a rule cannot split the id into), `v1_users/{uid}/v1_user_friends` (one half of a reciprocal friendship, keyed by the friend's UID and carrying their handle, mirrored under both users from the invitation onwards — written by the invite callable, read by the Menu screen's friend list and by the day screen, which shows what each friend answered) `v1_users/{uid}/v1_user_referrals` (one entry per newcomer this account brought in — the handle, what that referral paid, when it settled; written by the backend alone and **read by nothing yet**: it is the receipt a payout that moves two wallets has to leave, `referrals_count` being unable to say *who*, and it sits on the sponsor's side rather than being derived from `referred_by` because rules cannot scope a `list` to a filter — which also makes it one collection read the day a list is worth building), `v1_users/{uid}/v1_user_devices` (one Expo push token, the document id being the token itself — written by the app at every launch of a signed-in session, deleted at sign-out, read by the daily fan-out) and the calendar's two monthly read models, `v1_daily_question_months` and `v1_users/{uid}/v1_user_calendar_months` (which now carries `jokers.{DD}` alongside `days.{DD}` — the read model for the fifth calendar state, docs/prd.md §4.8). There is no per-day document: `v1_daily_question_months` is what maps a calendar day to the question that ran it. `apps/functions` owns seven domains. `users` is one callable, `users-deleteAccount`: it deletes the caller's answers, calendar months, push destinations, both halves of every friendship, username reservation, profile and Auth user, in that order — a callable because the rules deny every one of those deletes to every client, and because the questions' `answer_counts` are left standing on purpose (the answers stop belonging to anybody and keep counting in the aggregate). `friends` is two callables and a trigger: `friends-inviteFriend` resolves an exact handle against `v1_usernames` and writes both halves of the friendship in one batch, `pending` — a callable rather than a trigger because an unknown handle produces no write to fire on — `friends-getFriendCompatibility` answers how alike an accepted friend answered (docs/prd.md §5.3), a callable because comparing two histories is the one query `firestore.rules` denies every client: the answers' collection group is scoped to one's own, so that reading a friend's day never becomes reading their history. It checks the friendship before reading anything, caches its three numbers in `v1_friend_compatibilities/{pair_id}` and recomputes a pair at most once per Paris day, the score moving only when one of the two answers. **It reads `v1_user_calendar_months`, not the answers**, and only the months that moved since its own `synced_at`: the calendar is the read model that already carries each answered day's `option_id`, one document per user per month, so a year of history is twelve reads instead of three hundred and sixty-five — and the per-month tally on the pair document turns the recompute into a diff, which is what stops the cost from growing with the age of the two accounts. It cost ~7 300 reads a day at twelve months and ten friends consulted, ~40 now. The two exclusions come free from the source: a joker is projected into `jokers` and never into `days`, the onboarding demo into no month at all. And `friends-onFriendCreated` notifies the invited half, « Nouvelle invitation » over the inviter's handle, on its own Android channel and routing a tap to the Menu; it fires on both halves and pushes on the received one alone, so nobody is told what they just did themselves. `questions` is the other side of the StatFlouzz: `questions-proposeQuestion` debits `QUESTION_STATFLOUZZ_COST` (100) and writes the question `pending` in one transaction — a callable and the **only** way a question can be written now, `firestore.rules` having gone `allow create: if false` on `v1_questions`, since a price a direct write walks around is not a price — `questions-useJoker` is its cheaper twin (docs/prd.md §4.8): a callable that debits `JOKER_STATFLOUZZ_COST` (20) and writes a joker **on the same `v1_daily_question_answers/{uid}` document** as a regular answer, with `is_joker: true` and an empty `option_id`. The projection into `v1_user_calendar_months.jokers.{DD}`, the streak advance and the friend-answer badge fan-out then ride the shared `onAnswerCreated` trigger, which branches on `is_joker` — one path, halved read cost on the day sheet and the 18:00 nudge (one collection, not two). The callable refuses anything but today's still-open question or an already-done day; the client can never write `is_joker: true` (`firestore.rules`' `hasAnswerShape()` refuses it), so the callable is the only door. `questions-onQuestionUpdated` hands the money back when a moderator rejects a proposal, reading the `statcoin_cost` the question carries (so a seeded question, the demo and anything written from the console refund nothing) behind the `refunded_at` marker it checks in the very transaction that credits; it fires on every update to the collection, `answer_counts` included, and returns on the status before reading anything. `questions-onQuestionModerated` is the second step under that same trigger and closes the author's loop (docs/prd.md §4.7): it tells an author their proposal was approved, or refused — with the moderator's reason and, when there was one, the refund the money moved in silence until now — and it adds **no Cloud Function**, on the doctrine §4.9 states for the referral payout. It returns on the status before reading anything, so the `answer_counts` storm a drawn question takes all day still costs one invocation and no read; only a paid proposal is notified (`isPlayerProposal`, on `statcoin_cost` — the seeded catalogue, the demo and anything written from the console are credited to somebody who never wrote them); and its marker is **claimed inside a transaction rather than stamped afterwards**, because writing the marker is itself an update that fires the trigger on its own write. Two markers rather than one — `approval_notified_at`, `rejection_notified_at` — since a refund is final while a second verdict is news its author has every reason to hear. The other two moments an author is owed ride the 07:00 fan-out and register nothing either (`daily-questions/helpers/authorNotifications.ts`): the author of the question being drawn is told it is theirs, the author of yesterday's is told what it collected — a real count and the option that led, read off `answer_counts` through `leadingAnswer`, and nothing at all when nobody answered — each taking the slot the generic drop would have had in the per-user fan-out the 18:00 nudge already needed, so an author never gets two banners in a row and the same account writing both days gets the morning's. The three that are about the proposal travel on their own Android channel, `MY_QUESTION_CHANNEL_ID`; the morning one stays on the day's, since silencing the verdicts must not cost somebody the one morning their question runs. `sendPushToAllDevices` is gone with that change — `sendPushToUsers` with a constant callback is it. It also owns the one thing that makes somebody moderate: `questions-scheduleModerationDigest`, a scheduler every Wednesday at 08:00 Paris — an hour after the draw, so it reads the pot the morning left behind, and weekly rather than daily for as long as proposals arrive at a trickle — which mails the whole `pending` pot, oldest first, to every account holding the `admin` claim, and **sends nothing at all when the pot is empty**, a weekly mail that is usually empty being a weekly mail nobody opens; the body is an HTML file (`emails/moderationDigest.fr.html`) written to the same conventions as the password-reset template `firebase/email-templates/` holds — tables, inline styles, the hard shadow as a black table — inlined into the bundle by esbuild and read from disk by the ops script, so one copy serves both. `daily-questions` is the daily cycle: the daily scheduler runs at 07:00 Paris, draws the day's question, stamps its broadcast, indexes it in its month and queues the publication notification for immediate dispatch — which really sends, « La question du jour est tombée » over the question's own label, to the tokens the app now registers; a second scheduler runs at 18:00 and queues the evening nudge, which counts, per user, the accepted friends who have already answered (walked from the answerers, since a friendship is mirrored) and pushes « 4 de tes potes ont répondu à la question du jour. Et toi ? » to everyone who has not answered — « Personne n'a encore répondu. À toi d'ouvrir le bal. » when that count is zero — while whoever has already answered gets the other line, « Découvre la réponse de tes potes à la question du jour. », and nothing at all when none of them has answered; both travel on the 07:00 payload, so a tap opens the same day; a **third scheduler runs at 21:00**, the last-chance streak reminder of docs/prd.md §4.6, and it is the first notification of the day that is not for everybody — which is the whole of what makes it not harcèlement, the §9 question it settles. Its targeting is **one query**, `streak_last_answered_on == yesterday` (`helpers/streakReminder.ts`): a streak is alive only if its last on-time answer was yesterday, and the answer trigger writes that field for a joker exactly as for an answer, so « a déjà répondu », « a déjà posé son joker » and « traîne un streak_count de série morte » are three exclusions that cost no read at all — the answers are never touched. On top of it a `STREAK_REMINDER_MIN_STREAK` (7) floor, filtered in memory so no composite index is owed: a week is the shortest run anybody calls a série, it is the boundary docs/analytics.md's own `streak_bucket` already draws, and below it the 18:00 nudge already reaches everybody. The title carries the number (« Ta série de 23 jours va casser »), the body carries the deadline and the way out, and the two evening pushes were given a territory each — 18:00 the potes, 21:00 the série — which is why the nudge's zero-friends fallback stopped saying « ne perds pas ta série ». A wallet that can pay `JOKER_STATFLOUZZ_COST` gets `intent: 'joker'` on the payload, so a tap opens the day **and** the joker confirmation and saving a série is two gestures; a wallet that cannot is simply invited to answer and is never shown a price it cannot meet. It travels on its own Android channel, `STREAK_REMINDER_CHANNEL_ID`, which is the only opt-out it has — silencing it leaves the morning drop and the friend invitations alone, and **iOS has no equivalent**, so an iPhone can only mute the app whole until the profile grows a preference and §5.3 grows its settings screen. It is the one fan-out that goes through `sendPushToSomeUsers`, the third shape in `notifications`: `sendPushToUsers` pays a collection-group read of every device to reach a majority, which is right at 07:00 and at 18:00 and wrong here, where the recipients are a minority already computed — so it reads one device sub-collection per recipient, 20 at a time, into the same Expo batch. `helpers/streakReminder.ts` owns the select *and* the send (`sendStreakReminders`) so that `npm run run-streak-reminder` exercises the real code rather than a copy of it; the answer trigger increments the question's `answer_counts`, projects the day into the author's calendar month, moves their streak — paying `STREAK_STATFLOUZZ_REWARD` (100) into the wallet in that same transaction every `STREAK_STATFLOUZZ_MILESTONE` (10) consecutive days, docs/prd.md §4.7, the payout the proposal form now spends — and counts the answer onto **every accepted friend's** calendar month (`friend_answer_counts.{DD}`), which is what puts the « nouvelles réponses » badge on that day's calendar cell. No midnight closer yet. `instagram` is the newest domain and the only one registering **no Cloud Function**: it draws the three slides of the morning recap the Instagram account will post about the day before — the stat alone (« Comme 24 % des gens, tu es (peut-être) un.e PERFECTIONNISTE » — the result screen's own sentence, kept because a `stat_label` is written to finish « tu es un.e … » and reads as broken French under a plural subject, the adverb in the parentheses climbing with the share through `hedgeFor`'s five rungs, « peut-être » under 35 % to « forcément » past 90 %, so the sentence never undersells its own number nor promises what a plurality of 24 % cannot), then the question with every option's bar, then « Télécharge StatOwrel » — and nothing sends them yet. The order is the argument: the number is the only thing readable from a feed at thumb speed, the bars are what a post about statistics gets commented for, and the app is asked for last. `helpers/recapData.ts` reads the closed day through the month index and apportions the percentages so a column adds up to 100 rather than to 101, `helpers/recapCard.ts` draws all three on a `@napi-rs/canvas` at 1080×1350 (JPEG, the one format Instagram's `image_url` takes; 4:5, the tallest a carousel allows, and every slide at that size since each item is cropped to the first one's ratio), the first two cards leaning a few degrees opposite ways, at angles hashed from the date rather than drawn at random — a retried run has to redraw the slide it already uploaded identically, and the preview script has to show what will actually go out, and `helpers/brand.ts` mirrors `apps/app/src/design/tokens.ts` rather than importing it, depending on `@statowrel/app` being how Expo would end up in a Cloud Function bundle. The fonts are not committed: `scripts/lib/instagram-assets.mjs` copies them out of the `@expo-google-fonts` packages the app itself loads them from, into `dist/assets/` beside the bundle, since esbuild carries no `.ttf`. `npm run render-instagram-card` writes the JPEGs to disk through that very code — `scripts/lib/load-src.mjs` bundles `src/` with the deploy build's own settings so there is no second implementation to drift from the one that will post — and `--sample` draws five canned days without touching a project — 2 to 6 options, one dominant share per rung of that ladder — while `FIRESTORE_EMULATOR_HOST` points it at a seeded emulator for a real one. What it still owes: the Graph API call, the long-lived token and the scheduler. `referrals` is the parrainage of docs/prd.md §4.9, and it registers **no Cloud Function at all** — like `notifications` and `instagram`. Its payout is an answer handler and `daily-questions` already owns a trigger on that exact path, so a second `onDocumentCreated` there would have been a second Eventarc trigger, a second function and a second invocation on every answer given in the app, to settle something that happens once per account, ever; `dailyQuestions-onDailyQuestionAnswerCreated` calls `payReferralReward` after its own step instead, each keeping its own transaction so the referral never widens the one that moves the streak — and handing it the profile that step read inside that transaction, so deciding a once-per-account question costs no per-answer read either. It settles a referral on the newcomer's **first real answer** — not on their sign-up, an address costing nothing to invent — crediting `REFERRAL_STATFLOUZZ_REWARD` (30) to the sponsor and `REFERRAL_WELCOME_STATFLOUZZ_BONUS` (10) to the newcomer in one transaction — not split evenly, since bringing somebody in is work and naming a sponsor is a field typed once, and a reward that does not sit on the side of the effort does not fire, bounded by `REFERRAL_MAX_REWARDED` (20) per sponsor, and pushing to **both** sides — the sponsor learns *who* came from them, which is the whole point of the rail, the newcomer *why* their balance moved. The **demo question is dropped on its id at the call site, before anything is read**, since `useDemoAnswerFlush` writes the onboarding pick to that same path the first moment a session exists and would otherwise make the payout fire at sign-up; a payout that throws is logged and swallowed, the trigger not being configured to retry and the marker being the real retry (still null, so the next answer settles it); and `referral_rewarded_at` on the newcomer's own profile is the idempotency marker, stamped even when nothing can be credited (a deleted sponsor, a capped one) so a worthless referral settles once instead of retrying forever. The *opening* half lives in `users`: `users-onUserCreated` reads the `referred_by` the app wrote with the profile and, through `recordReferral`, puts the newcomer on the sponsor's `v1_user_referrals` list with `rewarded_at: null` **and** sends the sponsor a friend invitation in the newcomer's name — through `friends/helpers/createFriendshipPair`, extracted from `inviteFriend` when this second caller appeared, since what the two share is the *shape of a pair* rather than "send an invitation". A row exists from the sign-up and not from the payout on purpose: the payout can be days out, and a card empty until then reads as an attribution that failed. Refusing that invitation costs nothing — the payout never reads the friendship. `notifications` is the way out to a phone — the Expo Push transport, the collection-group read of every token, the sub-collection read of one account's own (`sendPushToUser`, what a notification addressed to somebody in particular goes through), the line-per-user fan-out the evening nudge sends through (`sendPushToUsers`) and the purge of the dead ones — and, since the digest, the way out to an inbox too: the Resend batch transport (`sendEmails`, its key a `defineSecret` rather than an environment variable) and the walk of Firebase Auth that turns the `admin` claim into a list of addresses (`listAdminEmails`), a custom claim being queryable from nowhere else. It stays the one domain registering no Cloud Function of its own: the other domains own the trigger, it owns the sending. `apps/app` opens on the **onboarding carousel** of docs/prd.md §5.6 the first time it is launched on a phone (`src/onboarding/`) — four slides saying what StatOwrel is, the last of them raising the notification permission itself rather than letting the cold system prompt be the first thing seen, then the **demo question** popped as the same red sheet the daily one wears: `v1_questions/01M0HNM3RQMP2TDXPTW6ZSSM17`, carrying the new `demo` status and the one thing the app lets anybody read with **no session at all** (`firestore.rules` grants that one `get`, never a `list`). The pick cannot be written there — an answer's id is its author's UID — so it waits in `AsyncStorage` and lands at the first sign-in (`useDemoAnswerFlush`), where it counts in the question's `answer_counts` alone: no calendar, no série, no « jours répondus », a demo not being a day. The starting tally is what `npm run seed-demo-question` puts on it. Whether the carousel has been seen is kept on the device, not on the account, since it precedes the account. Otherwise `apps/app` opens on the native splash screen `app.config.ts` configures — the star on the brand yellow, held until the persisted session resolves — and wears the same star as its icon (`assets/`). Behind it: its authentication flow (Google, Apple, email/password — reset link included, the « Mot de passe oublié ? » screen mailing it and Firebase's own page taking the new password — then the blocking sheet that asks for a unique username — `src/auth/`), the receiving half of the daily push (`src/notifications/` — one hook mounted from `App.tsx`, hanging off `useAuth()`: the three Android channels — the day's question, the friend invitations and « Mes questions », apart so silencing one leaves the others alone —, the permission asked once by the onboarding carousel and offered again — once per install, as a native alert, then permanently as the Menu's own button — to whoever was already signed in when that carousel shipped, the Expo token written to `v1_user_devices` as soon as the permission turns granted and deleted from `signOut()`, and a tap that opens whatever its payload names, the day or the Menu; a simulator, a stale dev client and a refused permission all end in a warning and nothing else) and two product screens. Stats (`src/stats/`) is the root of the app — streak, record, days answered and a month calendar, read from Firestore in two documents per month, and under the calendar the door of docs/prd.md §4.7 (`ProposeQuestionCard`): a whole card rather than a button, since a currency does not fit on one line — « Deviens acteur de StatOwrel », the earning rule as its subtitle (« Gagne 100§ pour chaque série de 10 réussie »), the wallet centred under it at the streak count's own scale over its unit, « StatFlouzz (§) », and the price carried by the button itself, in its `trailingLabel` slot rather than its label (« Poser une question » then « 100§ »). `§` is the StatFlouzz's symbol and the only form the interface shows past that one unit line, which is where it is taught; a screen reader is handed « 100 StatFlouzz » instead, a lone `§` being read as a section sign or skipped (`src/lib/statflouzz.ts` holds both forms, since the proposal sheet prices its own button too). That button now opens `src/questions/` — the proposal sheet of §4.7: the question and its 2 to 6 answers, each with its StatOwrel, through `useFieldArray`, a full-screen modal rather than a sheet, since it grows with the options it is given and is typed into with the keyboard up, and which writes nothing itself — `questions-proposeQuestion` debits and writes together, an empty wallet coming back as its own sentence rather than a « réessaie ». It closes on what the question cost, « Il te reste 40§ ». Reading those proposals back is the domain's other half, and it lives on the Menu screen rather than here — see the friend list below. Being *told* when one is approved, rejected, drawn or answered is now the backend's four author notifications: the two verdicts and the day-after recap arrive on their own Android channel and open the Menu on « Mes questions » (`pushRoute.ts`'s `my_questions`, which `MenuScreen` takes as a route param), the morning a question is drawn arrives on the day's channel and opens that day. The wallet is shown there and not on the stats strip: it belongs beside the price it pays. A cell carries a small pink bead, hung off its corner, when friends have answered that day since it was last opened: the month's own `friend_answer_counts` against what the device has already shown, held locally in `src/stats/data/seenFriendAnswers.ts` and levelled when the day is reopened. Its banner — the question while the day is still open, then, once the day is answered, the same red surface carrying **the mood it earned** and nothing else — neither the question nor a status line survives the answer: a check, « Aujourd'hui tu es un.e » and the StatOwrel under it in the result sheet's own type a step down, « Prochaine question à 7h » closing it, a tap reopening that result rather than doing nothing; the mood is the `stat_label` the calendar month already carries, so it costs no read — and its calendar cells open the day's question: `src/daily-question/` is the `DailyQuestion` route (today's day by default, any past day through its `date` param) — it shows the question large above its options and **takes the answer**: the double tap of docs/prd.md §4.3 writes `v1_questions/{question_id}/v1_daily_question_answers/{uid}` — document id = the Firebase Auth UID — and the sheet then **flips to the result of §5.5**, « Comme 10% des gens, tu es un.e BORDÉLIQUE » straight on the sheet, under it the one card left — the question and every option's share, one's own in yellow behind a tick — and under that the friends of §4.5, read one document per accepted friend once one has answered oneself — each row opening that friend's own screen, the same tap the Menu's list takes. The shares and the rarity are computed at display time from `answer_counts`. **The day an answer crosses a streak milestone, the celebration of docs/prd.md §4.6 lands between the phrase and the recap** (`components/StreakMilestoneCard.tsx`) — « 10 jours d'affilée », « +100§ » and the button that opens the proposal form, a palier being worth exactly one question and the payout having until now been the one reward of the product credited without ever being perceived. It is also the one thing on that sheet that is never replayed: `data/milestoneStore.ts` freezes `streak_count` and `statcoins_earned` the instant **before** the answer is written — after would be too late, the emulator running the answer trigger in milliseconds — and `data/useStreakMilestone.ts` shows the card only once the profile subscription proves the trigger credited at least what `streakStatflouzzReward` says that crossing is worth. Which is the whole rule: the payout is decided server-side while the sheet renders on the write, so nothing is announced that the account has not been credited, a late catch-up moves no streak and therefore celebrates nothing, and a milestone paid after the sheet was closed — an answer written offline — is simply never fêted, a missed celebration costing less than a broken promise. The watch is dropped when the sheet unmounts, which is what stops a day reopened from the calendar from replaying it. A joker takes the same card, with no StatOwrel above it. That result is also what an answered day reopens to from the calendar. Missing from it: the option's illustration and the share button. The header's other button opens `src/friends/`, the invitation sheet: a `formSheet` route where the friend's exact handle is typed, calling `friends-inviteFriend` and answering « Utilisateur introuvable. » under the field when nobody holds it. There is no tab bar: the menu — the account, the friends, the proposed questions and the settings — opens from the header's second button. The **friend list** of docs/prd.md §5.3 sits on the Menu screen (`src/menu/screens/MenuScreen.tsx` + `src/friends/components/FriendsCard.tsx`): one `onSnapshot` over `v1_users/{uid}/v1_user_friends` (`useFriends`), one card cut into rows by separators, invitations first — a pending one carries its answers as buttons under the row's note (« Accepter » / « Refuser » received, « Annuler » sent), while an accepted one carries a chevron and opens onto the friend's screen; refusing, cancelling and removing are all the same delete of both halves (`data/friendships.ts`). **An accepted row opens that friend's own screen** (`src/friends/screens/FriendScreen.tsx`, docs/prd.md §5.3): their streak, record and answered days — read straight off `v1_users/{friend_id}`, which any signed-in user may read, through the Stats screen's own `StatsStrip` / `StreakCard` / `StatTile`, a streak reading the same whoever it belongs to — and under it the **compatibility** with them, the one number in the app belonging to two people at once — on the `notification` pink, the only surface in the app built on it, since `primary` yellow already means « ta réponse » on the day sheet and « répondu » on the calendar. « Retirer ce pote » is that screen's own header menu, the row that opens it holding a chevron and nothing else. The card reads top to bottom as one sentence — the two faces overlapping, « Vous êtes compatibles à », the percentage, then the line that number is worth (« Même cerveau, deux téléphones. », « Pile ou face. »). How many days it was computed over is not shown — a headline that prints its own arithmetic invites the arithmetic to be argued with; the five-day floor is what keeps it honest instead. A raw agreement rate: identical picks over the days both answered, jokers and the onboarding demo excluded, nothing shown below `COMPATIBILITY_MIN_COMMON_DAYS` (5) shared days, since one shared day answered alike is 100 %. ## Conventions

### Code Style

- **Imports**: Use `@/*` path alias for intra-app imports (maps to `./src/*`). Use `@statowrel/models` for the shared package.
- **Forms**: use `react-hook-form` + `zod` (`@hookform/resolvers/zod`) — see `apps/app/src/auth/schemas.ts`. NEVER use raw `useState` for form state.
- **Functions API handlers**: validate request bodies with a `zod` schema using `.safeParse()`. NEVER use `.parse()` (throw-based) or `as` type assertions for untrusted input.

### Product Copy

Everything the user reads — a notification, a button, a screen, an e-mail — is written in French, tutoiement, in the app's own voice.

- **No em dash (`—`) in user-facing copy.** It reads as machine-written. Use a colon, a full stop, or recast the sentence. This applies to the strings only; the prose in code comments and documentation keeps it.
- Say nothing twice: a notification's body never repeats what its title already said.
- A number is the point of the sentence it sits in, or it does not belong there.

### Naming

- **Screens/components**: PascalCase.
- **Hooks**: camelCase with `use` prefix (`useSessionTimer.ts`).
- **Firestore collections**: `snake_case`, prefixed `v1_` for active data, and **plural** — `v1_questions`, `v1_users`, `v1_daily_question_months`.
- **Firestore fields**: `snake_case` (never camelCase).
- **Models**: named after their collection but **singular** — `v1_questions` is modelled in `packages/models/src/v1_question.ts`, exporting `QuestionFirebaseData` / `QuestionData` / `questionConverter` / `QUESTION_COLLECTION`. A sub-collection's name must be globally unique: a collection group is keyed by the last path segment alone.
- **Functions API handlers**: `handle{Action}.ts` (e.g. `handlePing.ts`).

### Firestore Data Rules

- Optional fields: ALWAYS `null`, NEVER `undefined`, NEVER omit the field.
- Timestamps: Use `UniversalTimestamp` from `@statowrel/models`, never ISO strings, in the raw/Firebase-facing type.
- New collections: ALWAYS use `v1_` prefix, ALWAYS plural.

### Auth (`apps/app`)

- Session and profile go through `src/auth/AuthContext.tsx` (`useAuth()`) — never call `onAuthStateChanged` from a screen.
- A signed-in account ALWAYS has its `v1_users/{uid}` document upserted by `src/auth/profile.ts`. **The document id is the Firebase Auth UID** — never a ULID, never a generated id. The document only exists once the username sheet has been through: `createUserProfile` reserves `v1_usernames/{handle}` first, then writes the profile — never in one batch, since the rules check the profile's username with a `get()` that a batch's own writes stay invisible to.
- Firebase error codes are translated in `src/auth/errors.ts`. NEVER surface a raw `auth/*` code to the user.
- Firestore refs in the app go through `src/lib/firestore.ts` (`getDocumentRef` / `getCollectionRef`), which wires the `@statowrel/models` converter — the client-side twin of `apps/functions/src/libs/firebase-admin.ts`.

### Firestore Converters

- **Reading timestamps**: ALWAYS use `parseTimestamp` from `@statowrel/models` in `fromFirestore`. NEVER inline `xxx.toDate().toISOString()` or write a new local helper. Patterns:
  - Required field with default: `parseTimestamp(data.xxx ?? null, 'now')`
  - Required with literal default: `parseTimestamp(data.xxx ?? null, '')`
  - Nullable field: `parseTimestamp(data.xxx ?? null)` → `string | null`
  - Why: legacy docs may have ISO-string timestamps written via raw `.update()` calls that bypass `toFirestore`. `parseTimestamp` accepts both `Timestamp` and `string`, so reads don't crash.
- **Writing timestamps via raw `update()` / `set()`**: ALWAYS use `Timestamp.now()` or `Timestamp.fromDate(new Date())` from `firebase-admin/firestore` (functions) or `firebase/firestore` (app). NEVER `new Date().toISOString()`. Firestore converters' `toFirestore` is **NOT** invoked by `DocumentReference.update()` — only by `set()` and on reads. Writing ISO strings via `update()` corrupts the document.

### Firebase Admin Helpers (`apps/functions`)

ALWAYS use the helpers from `@/libs/firebase-admin`. They wire converters and switch between emulator and prod consistently.

- **Read a document**: `getDocumentRef(collection, id, converter).get().then(parseData)` — returns `Identifiable<T> | null` with the `id` field merged in.
- **Read sub-documents / sub-collections**: `getSubDocumentRef(parentRef, sub, id, converter)` / `getSubCollectionRef(parentRef, sub, converter)`.
- **Read collection groups**: `getCollectionGroupRef(name, converter)`.
- **Read a trigger's event snapshot**: `parseSnapshotData(event.data, converter)` — a trigger hands over a raw snapshot, with no converter wired on it.
- **Read-then-write atomically**: `runTransaction(async (transaction) => …)`. A trigger is delivered at least once, so anything incrementing a counter reads a marker and bails out before writing.
- **Write batches / refs**: `createWriteBatch`, `createDocumentRef`, `createSubDocumentRef`, `getDocumentUpsertRef`.
- **Storage signed URL**: `getAdminStorageSignedUrl(path, filename?)` — pass `filename` to force `Content-Disposition: attachment; filename="..."`.

NEVER access `getFirestore()` / `snap.data()` / `bucket().file().getSignedUrl()` directly when a helper exists. NEVER duplicate these helpers locally.

### Functions Domain Structure

Every domain in `functions/src/domains/` follows this pattern — a domain holds only the folders it needs (`api/` is the shape an HTTP route would take; no domain ships one today):

```
domains/{domain-name}/
├── api/
│   ├── handlers/       # One file per HTTP route (handleXxx.ts)
│   ├── middlewares/     # Express middleware
│   └── index.ts        # Express app + onRequest export
├── triggers/
│   ├── steps/          # One handler per event type (onXxx.ts)
│   └── onXxxCreated.ts # Firestore trigger → dispatches to steps
├── helpers/            # Business logic utilities
├── tasks/              # Cloud Tasks handlers
├── schedules/          # Cloud Scheduler handlers
└── index.ts            # Exports Cloud Function registrations only
```

Top-level `functions/src/index.ts` uses namespace re-exports (`export * as questions from './domains/questions'`) — this produces function names like `questions-proposeQuestion` in Firebase.

### App (`apps/app`) — React Native / Expo

- Styling via React Native's own `StyleSheet.create`, colocated at the top of the component file and built from `src/design/tokens.ts` — never a raw hex, a magic padding or a hardcoded font name.
- **React Native Firebase** (`@react-native-firebase/{app,auth,firestore,functions}`), not the web `firebase` SDK — see `apps/app/src/lib/firebase.ts` and `docs/architecture.md`. Its modular API mirrors the web SDK's call for call, so the `@statowrel/models` converters work unchanged behind one cast in `src/lib/firestore.ts`. Three things it does differently:
  - **Nothing configures Firebase at runtime.** The default app is created natively at launch off `google-services.json` / `GoogleService-Info.plist` (`apps/app/firebase/`, gitignored, declared per variant by `app.config.ts`). Changing project takes a build, never a Metro restart.
  - **Error codes are namespaced** — `firestore/permission-denied`, not the web SDK's bare `permission-denied`; `auth/*` and `functions/*` are unchanged. There is no `FirebaseError` class to `instanceof`: use `isFirebaseError` / `firebaseErrorCode` from `src/lib/firebaseError.ts`.
  - **Adding a Firebase product is a native module** — a new `@react-native-firebase/*` package means rebuilding the dev client, not just restarting Metro.
- Navigation via [React Navigation 7](https://reactnavigation.org) — native stack + bottom tabs declared in `apps/app/src/navigation/`, entry point `apps/app/index.js` → `src/App.tsx`. Routes are typed through `RootStackParamList` / `TabParamList`, never route strings.
- **Design system**: neobrutalism (reference: [neoflux](https://neobrutalism.com/preview/templates/neoflux)) — bold colors, thick borders, hard offset shadows, and generously rounded corners (`sm` = 8px on the buttons, `DEFAULT` = 12px, up to 32px — never square). Every token — palette, radius, shadows, spacing, type scale, border width — lives in `apps/app/src/design/tokens.ts`, read by the components and the navigation theme alike. Components apply shadows through `apps/app/src/design/shadows.ts`, which hands React Native the CSS `boxShadow` string — the legacy iOS shadow props blur the edge once a surface has a corner radius, `boxShadow` stays crisp; fonts (Archivo Black, Space Grotesk) load via `expo-font` + `@expo-google-fonts/*`. The neobrutalism.com `shadcn` registry itself is web-only (Radix/Base UI need a DOM) — it does not apply to this React Native app; reusable component primitives are hand-built against these tokens (`apps/app/src/components/`) — `Avatar` is one such port, stacking its fallbacks instead of swapping them the way Radix does.

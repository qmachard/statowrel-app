# App (`@statowrel/app`)

React Native + Expo (managed workflow) + EAS. iOS + Android. Styled with React Native's own `StyleSheet`, composed from the design tokens.

The authentication flow exists (Google, Apple, email + password, the username sheet that follows a first sign-in, and the `v1_users/{uid}` profile it creates), and behind it the first product screen: **Stats** (`src/stats/`), the root of the app — no tab bar, the menu opens from a header button (docs/prd.md §5.1). It reads Firestore. See root `docs/architecture.md` for the overall plan.

**Design system**: neobrutalism visual style (reference: [neoflux](https://neobrutalism.com/preview/templates/neoflux)) — bold flat colors, thick borders, hard offset shadows, and generously rounded corners (`sm` = 8px on the buttons, `DEFAULT` = 12px, up to 32px — never square). Light mode only. Every token — palette, radius, shadows, spacing, type scale, border width — lives in `src/design/tokens.ts`; `rare`, `ultra` and `notification` are the only colours outside the identity palette — the StatOwrel result's rarity mentions (docs/prd.md §5.5) and the calendar's « nouvelles réponses » bead (§5.2) — marks, never a surface. Headings use `fonts.head` (Archivo Black), body text `fonts.sans` (Space Grotesk) — both loaded via `expo-font` + `@expo-google-fonts/*` in `src/App.tsx`. The neobrutalism.com registry itself (`shadcn` CLI, Radix/Base UI components) targets the web DOM and does **not** work with React Native — component primitives are hand-built against these tokens instead. `Button`, `TextField`, `Card`, `Calendar`, `BottomSheet`, `Avatar` and `DropdownMenu` exist in `src/components/`, plus the Lottie feedback animations in `src/components/animations/`; the rest lands with the screens that need it.

## Structure

- `index.js` — entry point: `registerRootComponent(App)`.
- `src/App.tsx` — root component. Loads the fonts, then `SafeAreaProvider` → `GestureHandlerRootView` → `NavigationContainer` (ref, theme, deep links) → `AuthProvider` → `RootNavigator`, holding the splash screen until the persisted session **and** the onboarding flag resolve. There is no JS launch screen: the splash is the native one alone (`app.config.ts`), hidden once `initializing` falls. `usePushNotifications()` is mounted here too, from inside both the provider and the container — it needs the session's UID and a navigator — and `useDemoAnswerFlush()` beside it, which writes the onboarding demo's pick once there is a UID to write it under.
- `src/navigation/` — [React Navigation 7](https://reactnavigation.org), same layout as `qmachard/checkpack-v3`. `RootNavigator.tsx` is a native stack that registers **only** the half of the app the session can reach (`SignIn`/`SignUp` signed out, `Stats`/`DailyQuestion`/`InviteFriend`/`Menu` signed in). There is no tab navigator: Stats is the root and Menu stacks on top of it (docs/prd.md §5.1), which is why `MenuScreen` carries its own back button. `types.ts` holds the param list (also registered globally as `ReactNavigation.RootParamList`), `linking.ts` the deep-link map, `navigationRef.ts` the imperative ref, `theme.ts` the container theme built from the design tokens.
- `src/design/tokens.ts` — the neobrutalism palette plus the `radius`, `shadows`, `fontSize` and `borderWidth` scales, the `fonts`, and `spacing(steps)` (one step = 4px). Read by every component's `StyleSheet.create` block *and* by the navigator chrome. One source, no drift.
- `src/design/shadows.ts` — the hard offset shadows as React Native styles, built from those tokens.
- `src/auth/` — everything authentication. `AuthContext.tsx` (`useAuth()`: `user`, `profile`, `initializing`, `needsOnboarding`, `completeOnboarding` — `profile` is a **subscription** to `v1_users/{uid}`, since the answer trigger moves its counters), `providers.ts` (Google / Apple / email primitives + `signOut`), `profile.ts` (`syncUserProfile` reads and mirrors Auth back, `createUserProfile` claims the username then writes `v1_users/{uid}` — **id = Firebase Auth UID**), `account.ts` (`deleteAccount` — the `users-deleteAccount` callable, then a local `signOut`: the app deletes nothing itself, the rules deny every one of those deletes to every client), `schemas.ts` (zod), `errors.ts` (French messages for `auth/*` codes, and for the `functions/*` ones the deletion raises), `SocialSignInButtons.tsx`, `OnboardingSheet.tsx` (the blocking username sheet, docs/prd.md §4.1), `screens/` (`SignInScreen`, `SignUpScreen`, both closing on the same `LegalLinks` footer as the Menu — pinned outside the scroll view and outside the keyboard avoider, so it stays at the bottom of the screen instead of riding the centred block or the keyboard). `signOut` drops this phone's push token *before* Firebase's own sign-out, while the delete is still a write the rules allow — see `src/notifications/`.
- `src/menu/` — what opens from the header's menu button (docs/prd.md §5.1), stacked over Stats with its own back button. `screens/MenuScreen.tsx` leads with the account on the page itself, no card around it — a big `Avatar`, the handle under it, the e-mail small under that — then the friend list of docs/prd.md §5.3 (`src/friends/components/FriendsCard.tsx`), and at the bottom the settings block that section asks for: signing out, « Supprimer mon compte » in `ghost` behind the native confirmation alert — a deletion is final, so it is asked twice, and the alert is the dialog both systems have taught their users to read — and under them `src/components/LegalLinks.tsx`, the two small grey links to the CGU and the mentions légales served by Hosting (`apps/admin/public/legal/`). Above that block, and only in a development build (`__DEV__`), « Revoir l'intro » clears the onboarding flag and the demo pick waiting to be written, then signs out — the carousel only ever shows to a signed-out session. The notification settings and the proposed questions land here as they come.
- `src/stats/` — the Stats screen (docs/prd.md §5.2), the app's root. `screens/StatsScreen.tsx` composes `components/` (`StatsHeader`, the friends' `InvitationsCard`, `DailyQuestionBanner`, `StatsStrip` holding `StreakCard` and the two `StatTile`s, `StatsCalendar` + its `CalendarDay` and `Hatch`, and `ProposeQuestionButton` closing the screen — the §4.7 door, locked until a 30-day streak, its condition carried by the button's own `description` line rather than by a card and a gauge), `helpers/calendarState.ts` derives the four day states and `helpers/streak.ts` the streak actually worth showing, and `data/useStatsData.ts` is the whole data source, over the month store in `data/calendarCache.ts`.

  **The calendar costs two documents a month, and that is the point.** The streak, the record and the answered-days total come from the `v1_users/{uid}` document `AuthContext` already subscribes to — free here. The displayed month is `v1_daily_question_months/{YYYY-MM}` (which days had a question) plus `v1_users/{uid}/v1_user_calendar_months/{YYYY-MM}` (which days this user answered, with the `stat_label` the cell renders). Never query `v1_daily_question_answers` for a month: that is one read per answered day plus its question to join, which is exactly what those two documents exist to avoid.

  **A month is read, never subscribed to, and kept once read.** `data/calendarCache.ts` is where it is kept — a module-level store keyed by user and month, which `useStatsData` reads through `useSyncExternalStore` so a month landing moves the screen without being pushed into React state. Almost nothing writes into a calendar month while the screen is up: this user answering, the 07:00 draw landing while the app was in the background, and — the one that comes from somebody else — a friend answering, which moves the badge counter alone. So each is picked up at a moment it can be — for two reads — rather than by holding two open connections per visited month through the hours nothing happens, and a chevron back to March costs two reads the first time and nothing after.

  **The refresh policy is three rules.** Answering marks that month as behind (`rememberAnswer` → `invalidateCalendarMonth`) — marked, not dropped, since throwing it away would blank the calendar behind the question sheet. Coming back to the screen re-reads it (`useFocusEffect`, every focus but the mount). And pulling the screen down re-reads it on demand, which is what the `RefreshControl` on `StatsScreen`'s scroll view is for. Between the app's write and the answer trigger's projection, `answerStore` lays this session's own answers over the month that was read, so a day answered a second ago is checked whether or not the trigger has caught up.

  **The badge on a day is two numbers.** `v1_user_calendar_months` carries `friend_answer_counts.{DD}` — how many accepted friends answered that day, written by the answer trigger under every friend of whoever answered — so it arrives with the month and costs no read of its own. Against it, `data/seenFriendAnswers.ts` holds what this device has already shown, per day: a module store mirrored to `AsyncStorage`, keyed per account, read through `useSeenFriendAnswers` and marked from the question sheet the moment the friends' list is on screen. Local on purpose — « déjà vu » is a property of a screen someone looked at, not of the account, and `v1_user_calendar_months` is backend-owned (`allow write: if false`) — so a second phone rebadges each day once. The mark is the *highest* of what the sheet listed and the day's own counter, because that counter never goes down: a friend removed since they answered would otherwise leave a dot nothing could clear. Only a day one has answered is badged, since a friend's answer is unlocked by one's own (docs/prd.md §4.5).

  The daily-question banner rides along on the same two documents — its label is copied onto the month index and "already answered" is a day of the user's month, or an answer this session has just written — so it costs nothing either. It reads the *current* month rather than the displayed one, which is why `useStatsData` returns `todayQuestion` and `answeredToday` beside `calendar`: browsing back to March must not make today's question vanish from the top of the screen.
- `src/daily-question/` — one day's question (docs/prd.md §5.4), the sheet that lands on top of Stats. `screens/DailyQuestionScreen.tsx` puts the close button on its own line and the question under it as the sheet's title — no label above it — and drives the **double tap** of §4.3 through `helpers/useDoubleTapAnswer.ts` — first tap selects, second one validates behind a 150 ms guard, and the onboarding demo mounts the very same hook so the app's signature interaction cannot be timed two ways — `components/QuestionOption.tsx` renders the two states it drives (and owns `letterOf`, the A / B / C of its badge), and `data/` is the day: `useDailyQuestion.ts` reads `v1_daily_question_months/{YYYY-MM}` once to learn which question ran the day — a day's entry never changes — then subscribes to that `v1_questions` document (its `answer_counts` moves on every answer, and the 07:00 drop then lands on a screen already open) and to the answer. `submitAnswer.ts` writes the answer at `v1_questions/{question_id}/v1_daily_question_answers/{uid}` (**document id = the Firebase Auth UID**, which is what makes one answer per person per day a property of the data — one question is one day), dating it with the question's own `broadcast_on` and flagging `late` against its `closes_at`, since those are the values the rules check. `answerStore.ts` is what the Stats screen leans on the moment an answer lands: it marks the answered month as behind in the calendar cache, and holds the day as the answer trigger will project it — option, `stat_label`, `late` — so the banner falls and the calendar cell is checked on the tap rather than on the trigger, whichever of the two the next read beats. The write is the app's only one under a question: `answer_counts`, the calendar month and the streak all belong to the answer trigger.

  **An answered day shows the result, not the question.** The sheet's content forks on the answer — one branch covering both the flip after the second tap and the read-only reopening from the calendar, since both are « there is an answer » — into three blocks. `components/StatOwrelHeadline.tsx` says the phrase and the StatOwrel straight on the sheet's own colour (`helpers/surface.ts` holds the two surfaces and their foregrounds, shared by the screen and by what it lays on them), `components/AnswerRecap.tsx` is the only framed surface left — the question, then one `components/AnswerShareRow.tsx` per option, its share as the width of the fill behind its label and the picked one in `primary` behind a tick — and `components/FriendAnswers.tsx` closes it with the friends of §4.5. The card frame that used to hold all of it is gone; rarity survives as a mention beside the date. `helpers/statowrel.ts` is the computation behind it, unchanged. Two things it does on purpose: it folds this user's own answer into the counts, because the answer trigger increments `answer_counts` a beat after the app writes the answer and the phrase would otherwise open on « 0% »; and it sums over the question's own options rather than over every key of the map, so a stale key cannot inflate a denominator. Rarity is never stored — it is that map's shape at display time, which is why the question is subscribed to.

  **A friend's answer is a read, never a query.** `data/useFriendAnswers.ts` reads neither the friend list nor the pictures — `src/friends/data/useFriends.ts` already subscribes to `v1_user_friends` for the Menu screen's list, and `useFriendAvatars` already reads a profile per UID and caches it. It adds one `get` per accepted friend on `v1_questions/{question_id}/v1_daily_question_answers/{friend_id}`, the document id being the answering user's UID. A collection-group query is deliberately impossible: `firestore.rules` only ever lets one group-query one's own answers, so a friend's stays scoped to one question — one question is one day. Nothing is read before the current user's own answer exists; that is the mechanic of §4.5, not an optimisation. The rows are `src/friends/components/FriendRow.tsx` in a card cut by separators, exactly as on the Menu screen, so a friend keeps the same face and the same line wherever they appear — the picked option goes in the row's action slot, the hour in its note. Nothing is subscribed to, the list carries no scroller of its own — the sheet's whole column is the scroller, so the friends read as one list rather than through a three-row window — and with no friend at all the section is one line on the sheet rather than an empty card.

- `src/friends/` — inviting a friend by handle (docs/prd.md §4.1) **and reading the friendships back** (§5.3). `data/useFriends.ts` is one `onSnapshot` over `v1_users/{uid}/v1_user_friends`, split by `friendshipDirectionOf` into accepted friendships, invitations received and invitations sent — subscribed rather than fetched, since the callable's batch lands a beat after the sheet closes and an acceptance comes from the other user's device. `components/FriendsCard.tsx` renders that on the Menu screen: the title with the invitation button beside it, then one card cut into rows by separators — the pending invitations beside the accepted friendships (both halves exist from the invitation onwards, so hiding them would lose the one received), the ones waiting on this user first, and §5.3's own sentence when there is nobody. `data/friendships.ts` writes the answer: accepting moves both halves to `accepted` in one batch, and refusing, cancelling and removing are the same delete of both halves — which is why a pending invitation carries its two answers as buttons under the row's note — `components/PendingActions.tsx`, « Accepter » / « Refuser » received and « Annuler » sent — while the dropdown menu, in `ghost`, is left to the accepted friendships and their « Retirer ce pote ». `components/InvitationsCard.tsx` carries the invitations received to the top of the Stats screen as well: the same row, one card each with no heading over it, on a horizontally scrolling line so several of them cost the screen the height of one, and nothing at all when nothing is waiting. Both cards write through `data/useFriendshipWrite.ts`, which holds *which* write is in flight so a row showing two buttons only spins the one that was tapped. The handle per line is the `friend_username` copy carried on the entry — one collection read for N friends — which is also why no streak is shown: it is not copied, and it would be stale if it were. The picture is not on the entry either, so `data/useFriendAvatars.ts` reads it from each friend's profile, once per UID and cached for the session. The invitation itself: `screens/InviteFriendScreen.tsx` is a dismissable `formSheet` sized by its own content, like the daily question and unlike the blocking onboarding sheet — nothing is blocked on inviting somebody. `screens/InviteFriendScreen.tsx` is a dismissable `formSheet` sized by its own content, like the daily question and unlike the blocking onboarding sheet — nothing is blocked on inviting somebody. That sheet is the app's only feature that **writes nothing itself**: `data/inviteFriend.ts` reads the `v1_usernames` reservation — `get`-able by any signed-in user, which is how a handle resolves to an account — and only then calls the `friends-inviteFriend` callable, which resolves the handle again and writes both halves of the friendship. The client-side read is a **shortcut, not the check**: it spares a function invocation and its cold start on the screen's likeliest outcome, a typo, while the callable stays the one that decides, since a client's word on who exists is worth nothing. Everything that fails lands under the field, because the handle is the only thing the user can change here — `errors.ts` maps the `functions/*` codes to French the way `src/auth/errors.ts` maps `auth/*`, and an unknown handle and a malformed one share one sentence on purpose (there is no public search, so both mean « personne ne s'appelle comme ça »). Once it has been through, the form is replaced by what happened rather than left standing with a message under it.

- `src/onboarding/` — the carousel a fresh install opens on, before the sign-in screen (docs/prd.md §5.6). `screens/OnboardingCarousel.tsx` is a paged horizontal `ScrollView` over `copy.ts`'s five slides — the last of them, « C'est parti », being the only one whose button does not advance: it opens the demo, and it is dropped from the list when there is no demo to open — `components/OnboardingSlide.tsx` for the wording, `components/OnboardingVisual.tsx` for what sits above each title — the star, a sample StatOwrel card, three generated faces, a bell, and the success check on « C'est parti »; the two Lottie ones hold their last frame between plays rather than looping, since every slide is mounted from the first render and a play-once animation would be over before anybody reached it, `components/OnboardingDots.tsx` for where one is. It is rendered **beside** the navigator from `src/App.tsx`, like the username sheet and for the same reason: there is no session yet to navigate under. `data/useOnboardingSeen.ts` keeps « already seen » in `AsyncStorage`, on the **device** rather than on an account — the carousel precedes the account — and storage it cannot read counts as seen; the splash is held until that flag resolves as well as the session. `resetOnboardingSeen` clears it and tells the hook on the spot, through a small set of listeners in that same module — it exists for the Menu's `__DEV__` button alone, since testing the carousel would otherwise mean clearing the app's storage between runs.

  **The demo question is real, and its answer lands one sign-in later.** `data/useDemoQuestion.ts` reads `v1_questions/{DEMO_QUESTION_ID}` once by its fixed id — the app's only Firestore read with no session behind it, which is what the `demo` status and its `allow get` in the rules exist for — and `components/DemoQuestionSheet.tsx` poses it in the same red sheet as the daily question, through the same `useDoubleTapAnswer`, `StatOwrelHeadline` and `AnswerRecap`.

  The pick cannot be written there: an answer's document id *is* its author's UID, and the carousel runs before there is one. So `data/demoAnswerStore.ts` keeps it in `AsyncStorage` and `data/useDemoAnswerFlush.ts` — mounted from `src/App.tsx` beside the notification hook, hanging off `useAuth()` for the same reason — writes it at the first session, through the same `submitAnswer`, which carries the empty `date` and the `late: false` the rules pin a demo answer to. It then counts in `answer_counts` and in nothing else: no calendar entry, no streak, no `answers_count`, and nothing near `answerStore`, since a demo is not a day. The pick is dropped once it has landed, or once the answer it would create is read back as already there — never on the strength of the error, since a `permission-denied` on a project whose rules are not deployed yet is exactly the failure this meets first, and reading it as « already answered » would throw the pick away. Every other failure leaves it for the next launch, and the warning carries the code. The tally it starts from is `npm run seed-demo-question`'s, an empty map opening on « 100% des gens ». No question to read simply ends the carousel a slide early, never a step to be stuck on.

  **The notification slide raises the permission dialog** — `requestPushPermission`, which asks and registers nothing, there being no account yet. A refusal is final on both platforms, so the cold prompt at the first signed-in launch is the one thing worth moving: the slide says what will be sent, its « Suivant » asks, and the carousel moves on whatever the answer. The token lands later, at the first signed-in launch.

- `src/notifications/` — the receiving half of the daily push (docs/prd.md §4.2), the whole thing driven by `data/usePushNotifications.ts`, mounted once from `src/App.tsx`. It hangs off `useAuth()` because both halves need a UID: `data/deviceRegistration.ts` writes `v1_users/{uid}/v1_user_devices/{push_token}` at every launch of a signed-in session — Android channel first (`DAILY_QUESTION_CHANNEL_ID` from `@statowrel/models`, without which Android silently drops the notification), then `getExpoPushTokenAsync({ projectId })` off `extra.eas.projectId` — and `signOut()` deletes it, since the token belongs to the *phone* and not to the account. The document id is the token, so re-registering is a write to the same document; `created_at` is read back rather than restamped, `updated_at` is what a launch moves.

  **Nothing here may fail a launch.** `helpers/nativeModule.ts` requires `expo-notifications` lazily, the same trick `src/auth/nativeModules.ts` plays and for a stronger reason — this is mounted at the root of the tree, where a throw takes the whole app down instead of one button — and the registration swallows its own errors: a simulator (`getExpoPushTokenAsync` rejects there), a refused permission and a stale dev client are all ordinary. A refusal is never re-prompted: `canAskAgain` is false after the first « non » — and the launch registration does not even ask, it settles for the permission it finds (`ask` defaults to false). The one place that asks is `requestPushPermission`, called by the onboarding carousel's notification slide, which has just said what the notification is for; it registers nothing, the carousel running before there is an account.

  **A tap opens a day.** The push carries `{ type: 'daily_question', date }`, parsed with `zod` in `helpers/pushRoute.ts` — it comes off the network and is read before any screen, so an unknown payload has to end in nothing happening. The tap that *launched* the app is read from `getLastNotificationResponseAsync()` beside the listener, both deduplicated by the notification's identifier since Android delivers a launching tap twice. `helpers/openDailyQuestion.ts` navigates through `navigationRef` and waits for the container to be ready: on a cold start the tap is read on the very commit the navigator mounts on.

- `src/lib/functions.ts` — the callable client: `getFunctions(app, REGION)` with the emulator hookup, and `callFunction(name, payload)` typed through the contract of `@statowrel/models`'s `callables.ts`. `REGION` mirrors the backend's `REGION_CLOUD` — a mismatch is a runtime 404, not a compile error, so the two are changed together.

- `src/components/` — neobrutalism primitives (`Button`, `TextField`, `Card`, `Calendar`, `BottomSheet`, `Avatar`, `DropdownMenu`), plus `LegalLinks` — the CGU / mentions légales footer, here rather than under a domain because both doors into the app and the Menu carry it. `DropdownMenu` stands in for the Radix-based original: React Native has no popover layer, so the panel is a transparent `Modal` positioned against its trigger measured in window coordinates — which is also how it escapes a row's `overflow: hidden` — and it flips above the trigger when the bottom of the screen is too close. `Avatar` stacks its fallbacks rather than swapping them the way Radix does: initials at the bottom, always local; a DiceBear « patchwork » SVG seeded on the handle over them (`src/lib/avatars.ts`, the app's own palette, rendered through `react-native-svg`'s `SvgUri`), so an account has a face before it has a picture; and the profile's own `photo_url` on top when there is one, dropped on load failure to reveal the generated one. `BottomSheet` blocks by default — that is why it exists, over the dismissable `formSheet` routes — and takes two optional props for the onboarding demo alone: `onDismiss`, which makes the scrim and the Android back button close it, and `surface`, which puts its content on the daily question's accent red instead of the app's cream. `Card` and `Calendar` are React Native ports of the [neobrutalism.com](https://neobrutalism.com/docs/components/card) components: same anatomy, minus the `has-*` variants and the DOM-only `react-day-picker`. An icon-only button is `Button` at an `icon*` size, not a separate component.
- `src/components/animations/` — the Lottie feedback animations, on `lottie-react-native` (a **native** module: adding it means rebuilding the dev client). `sources.ts` is the registry of the `assets/lottie/` compositions, `Animation.tsx` the sized wrapper reading it (its `replayDelay` holds the last frame before playing again — Lottie's own `loop` restarts on the next frame), and `SuccessCircle` / `SuccessCheck` / `Star` the presets that pick a composition. A new animation is a JSON in `assets/lottie/` plus a line in the registry.
- `src/components/illustrations/` — static SVG art on `react-native-svg`, sized by a plain `size` in pixels. `StarPeeled` is the mark the star sticker leaves when it comes off, traced from the contour of `assets/lottie/star.json` and kept in that composition's 512×512 canvas so it lands where the animation sat. Anything that does not move belongs here rather than in `animations/`.
- `assets/` — the Lottie compositions in `lottie/`, and beside them the three 1024×1024 PNGs the native side needs, all three the same star: `icon.png` (the app icon, drawn on `primary`), `adaptive-icon.png` (its Android foreground layer) and `splash-icon.png` (the launch screen's star, cut out over the same `primary`). The two transparent ones are framed against the masks that will crop them, not against their own edges: the star takes 66% of the adaptive layer, the most that keeps it clear of the circle a launcher may mask down to — the trail runs past it, the way it runs off the icon — and a bit under half of the splash layer, which is what makes it fill Android's own circle at `imageWidth: 288`. In both, the `imageWidth` sizes the **square**, not the star. They are the native chrome, so changing one takes a build, never an OTA update.
- `src/lib/haptics.ts` — the light / heavy+success taps of the double tap (docs/prd.md §4.3). `expo-haptics` is required lazily and every call swallows its failure, so a device with haptics off still validates.
- `src/lib/useSheetBottomInset.ts` — the room every sheet keeps under its content so the system bar doesn't cover it. No sheet is inset from below by the platform: react-native-screens avoids only the top inset of a `formSheet` on Android, and a `Modal` window is edge-to-edge there too. Spent as a plain `paddingBottom` rather than left to `SafeAreaView edges={['bottom']}` — that padding is computed natively *after* the first layout, while a `fitToContents` detent has already measured the content and kept the height it measured.
- `src/lib/dates.ts` — local-calendar helpers keyed on the model's `YYYY-MM-DD` strings, plus the French month/weekday labels. No UTC round-trip: `toISOString()` would move the day.
- `src/lib/firebase.ts` — Firebase client SDK (`firebase` npm package, not `@react-native-firebase`) init: `app`, `auth` (persisted via `@react-native-async-storage/async-storage`), `db`, plus the Auth and Firestore emulator hookups. Same client SDK the rest of the monorepo uses, so `@statowrel/models` converters work unchanged.
- `src/lib/firestore.ts` — `getDocumentRef` / `getSubDocumentRef` / `getCollectionRef` / `getSubCollectionRef`, each wired with a `@statowrel/models` converter. Use these rather than calling `doc()`/`collection()` directly.
- `app.config.ts` — dynamic Expo config. Declares the config plugins — `expo-apple-authentication`, `expo-notifications` (the push entitlement on iOS, `POST_NOTIFICATIONS` on Android; without it a build takes a token and never shows a banner) and `expo-splash-screen`, plus Google's when its URL scheme is set. Carries the icon and the native splash (their backgrounds, the images, and the smaller width Android's masked canvas caps them at) — `BRAND_YELLOW` is written out by hand, since the Expo CLI reads this file outside Metro and cannot resolve an import of the token module. Reads `APP_VARIANT` (`development` | `preview` | `production`, set per EAS build profile in `eas.json`) to pick app name / bundle identifier / package name. `development` gets its own `.dev` suffix and sits beside either of the others on a device; **`preview` and `production` share one identifier** — a Google OAuth iOS client and a Sign in with Apple capability are bound to a bundle identifier, so a preview with its own would need a third of each, for a variant whose job is to be what production will be. The trade is that those two cannot coexist on a device: installing one replaces the other, and only the app name tells them apart. **It throws when `APP_VARIANT` is missing or unknown, and never defaults**: a default is the one failure this file can have that leaves no trace — a `--profile production` build would go green from end to end carrying the `.dev` bundle identifier. Which is why `dev`, `prebuild` and `submit:*` set the variant inline in `package.json`, and why anything else run by hand has to pass it (`APP_VARIANT=production npx expo config`).
- `eas.json` — EAS Build & Submit profiles: `development` (dev client, internal), `preview` (internal, auto-incremented), `production` (store-ready, auto-incremented). Preview auto-increments because it shares production's application identifier, and `appVersionSource: remote` counts build numbers per identifier: without it the two would mint duplicates against the same counter.

## Conventions

- Style with a `StyleSheet.create` block colocated at the top of the component file, built from `src/design/tokens.ts` — never a raw hex, a magic padding or a hardcoded font name. Variant maps (per-variant surfaces, per-size paddings) are `StyleSheet.create` records keyed by the variant, composed through a style array at the call site.
- A reusable component takes a `style` prop for **layout only** (`flex`, margins); its surface and its shadow stay props of the component (`variant` / `shadow` on `Card`), so a caller can't half-override a variant.
- Firestore reads/writes ALWAYS go through a converter from `@statowrel/models` — use `getDocumentRef` / `getCollectionRef` from `src/lib/firestore.ts`, never read `snap.data()` untyped.
- Forms use `react-hook-form` + `zod` via `@hookform/resolvers/zod`, never raw `useState`.
- Auth session state comes from `useAuth()`; never call `onAuthStateChanged` from a screen.
- Subscribe to what moves **under an open screen**, read what does not: `v1_users/{uid}` and a broadcast question's `answer_counts` both move while the user is looking at them, and a `getDoc` would have to guess when. A calendar month does not — nothing but this user's own answer and the 07:00 draw writes into one — so it is read, cached, and re-read at the moments that can carry it: the answer, the return to the screen, the pull. When a read can land before the trigger that would have moved it, cover the beat rather than reaching for a listener (`answerStore`). A hook that resets state at the top of an effect to switch keys trips `react-hooks`; carry the key on the state and derive what is current, as `useDailyQuestion` does.
- The React compiler's `preserve-manual-memoization` is an **error** here, not a warning: a `useCallback` may not depend on a value the hook also returns (the compiler treats what escapes as mutable), and may not `setState` synchronously inside an effect. Both are what pushed the calendar cache out of the hook and into a module store — see `data/calendarCache.ts`.
- Public env vars (safe to embed in the client bundle) are prefixed `EXPO_PUBLIC_` and read via `process.env` — see `.env.example`. Never put a secret behind `EXPO_PUBLIC_*`.
- A screen is a named export in `src/<domain>/screens/<Name>Screen.tsx`, registered in `src/navigation/`. Navigate with `useNavigation()`; add the route to `RootStackParamList` first, so the call is type-checked.
- Every dependency Expo manages must stay on the version its SDK bundles (`npx expo install --check`) — a newer major of a native module is a broken native build, not an upgrade.

```bash
npm install

```

Firebase itself needs no native linking (this app uses the JS `firebase` SDK), but Google and Apple sign-in do (`@react-native-google-signin/google-signin`, `expo-apple-authentication`), so the dev client must be rebuilt after changing their config.

## Environment variables

Every value has to be declared **twice**, because two different processes read them and neither sees the other's source:

- `.env.local` — read by Metro when you run the app locally.
- one of the two EAS sources below — read when EAS builds the binary. `.env.local` is gitignored, and EAS excludes gitignored files from the upload, so a value that only lives there is simply absent on the builder.

EAS itself has three sources, in increasing order of precedence: the build profile's `env` block in `eas.json`, then `.env` files, then the **EAS environment variables** stored on Expo's servers. A same-named variable higher in that list wins — which is why nothing important should be defined in two of them at once. All three are applied on the worker *and* when the EAS CLI evaluates `app.config.ts` locally to resolve credentials, so a build cannot resolve one bundle identifier and sign another.

Which EAS environment a build reads is derived from the profile unless the profile names one with an `environment` field: `production` when `distribution` is `store`, `development` when `developmentClient` is true, `preview` for everything else. Here that lands on the environment of the same name as each profile.

The split between the two EAS sources follows whether the value changes between environments:

| Variable | Lives in | Why |
|---|---|---|
| `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `…_IOS_CLIENT_ID`, `…_IOS_URL_SCHEME` | `eas.json` `env` | Public OAuth identifiers, committed on purpose — the reviewer of a diff should see which client a profile signs against. |
| `EXPO_PUBLIC_FIREBASE_*` | EAS environment variables (`eas env:create --environment <env>`) | Per-environment by nature: `.firebaserc` points both the `default` and `production` aliases at `statowrel-app` today, so the six values are the same in the three EAS environments, but they are what has to diverge the day the production project splits off. Not secrets — the Firebase web config is public — just environment-shaped. |

Verify what a profile actually resolves to before trusting it: `npx eas config --profile production --platform ios` prints both the loaded variables and the resulting config, and `npx eas env:list --environment production` (add `--scope account` for the account-wide ones) prints what the servers hold.

Two things fail loudly rather than silently, both because their silent version cost a wasted build:

- `app.config.ts` throws when `APP_VARIANT` is missing or unknown — see the file's own comment.
- `src/lib/firebase.ts` throws when `EXPO_PUBLIC_FIREBASE_API_KEY`, `…_PROJECT_ID` or `…_APP_ID` is missing, instead of letting `initializeApp()` accept `undefined` and surfacing it later as an `auth/invalid-api-key` from whatever screen touched Auth first.

Google sign-in needs three public OAuth identifiers: `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` (the one Firebase mints id tokens for), `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`, and `EXPO_PUBLIC_GOOGLE_IOS_URL_SCHEME` (the reversed iOS client id). Leave them empty and the Google button hides itself; the rest of the app still runs.

That last one is the one to watch: `app.config.ts` reads it at **config-evaluation** time to register the URL scheme natively. Miss it on the builder and the binary ships without the scheme while the JS bundle still believes Google is configured — the native SDK then fails on tap with "Your app is missing support for the following URL schemes". Changing it always requires a new build, never just a Metro restart.

The iOS client id and its URL scheme are bound to a **bundle identifier**, so a variant can only carry a pair minted for its own. `development` has its own client; `preview` and `production` share one, because they share an identifier (see `app.config.ts`). The web client id is project-wide and the same for all three. A variant left without an iOS pair keeps the Google button hidden on iOS rather than failing on tap.

## EAS Build & Submit

Requires `eas login` once. The EAS project is already linked — `@qmachard/statowrel-app`, its `projectId` is hardcoded in `app.config.ts` under `extra.eas.projectId` (a public identifier, not a secret; the dynamic config means EAS can't write it there itself). The `slug` must stay `statowrel-app` to match that project.

```bash
npm run build:dev:ios       # eas build --profile development --platform ios
npm run build:dev:android
npm run build:preview:ios
npm run build:preview:android
npm run build:prod:ios      # eas build --profile production --platform ios
npm run build:prod:android
npm run submit:prod         # submit:prod:ios + submit:prod:android
```

All of the above are also exposed as root-level `npm run <script>` commands (see root `package.json`). They deliberately bypass Turbo and call the workspace script directly (chained after `build:models`, since `@statowrel/models` resolves to `dist/`): `eas build` / `eas submit` are interactive, and Turbo only forwards stdin to a task under its full-screen TUI.
